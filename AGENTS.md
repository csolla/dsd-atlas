# DSD Atlas

DSD's project management tool: campaigns (projects), tasks, time logging and director dashboards. Built for the Marketing team as the Marketing PM Tool and renamed DSD Atlas on 16 November 2026; it replaces Asana for every DSD department from go-live on 14 December 2026 (plan: https://claude.ai/artifact/Q9jZ9Rvc3mx7iCKN9cUytS).

- **Live app:** https://csolla.github.io/dsd-atlas/ (GitHub repo `csolla/dsd-atlas`).
- **The old Atlas is retired.** The earlier tool also called Atlas (repo `csolla/dsd-projects`, now archived, folder `../archive/atlas-old`) is switched off. Don't change it, analyse it or compare against it.

- **Stack:** plain HTML, CSS and JavaScript (no build step), hosted on GitHub Pages, with a new, dedicated Supabase project for the database, login, file storage and live updates.
- **Owner:** Carlota (csolla@digitalsmiledesign.com), who is not technical. Explain each step in plain language.
- **SQL:** Carlota runs database changes by hand in the Supabase SQL editor. Save each one as a numbered file under `supabase/migrations/` and put it on her clipboard with `pbcopy`.

## Build history

All five build milestones are complete (October 2026). The original PRD, milestone prompts and milestone logs were moved out of this folder to `../archive/marketing-pm-tool-build-plan/`. They are a historical record, not current documentation: the code has moved past some of their decisions, and nothing in the code depends on them. The milestone logs are still the best summary of why things were built the way they were.

- Database changes so far: `supabase/migrations/01` to `26` (17–19 add the first templates and their owners; 20–22 add personal to-dos; 23 adds the Content Orbit and Planning Center product templates; 24 adds template roles; 25 prepares the Asana import; 26–28 add forms; 29 adds rules; 30 favourite projects; 31–32 portfolios; 33 favourite portfolios). The next one is `34`.
- **Template owners:** template tasks start with "Usually done by: <Asana name>". `19_template_owners_by_email.sql` assigns them to Atlas people by work email (names differ between Asana and Atlas) and can be re-run whenever more people join; add new names to its list.
- **Templates (must-have 6, `16_templates.sql`):** a template is a campaign with `is_template` (set at creation, never changed). Templates show only in Projects → Templates, can't have time logged (`block_time_on_archived`), and `notify()` skips their tasks. `copy_project(source, values jsonb, as_template)` (security invoker) copies sections, custom fields, tasks then subtasks (status reset to To do, due dates shifted by the start-date difference, an assignee who can't see the copy dropped), field values and campaign_access. Used by New project → Start from, "Use this template" and "Save as template". **Roles** (`24_template_roles.sql`): `tasks.template_role` (text, set in the task panel of a template task; subtasks without one follow their main task). New project → Start from shows a person picker per role and passes `p_values.roles` = {role: person id}; `copy_project` gives that role's tasks to that person, else keeps the template assignee. DSD Clinics Onboarding has Account manager (Michelle's tasks) and Coach (Lindi's). My tasks, My time, the time form, Dashboards and person search leave templates out; keep that true for any new list of tasks or projects.
- **Custom fields (must-have 5, `15_custom_fields.sql`):** `custom_fields` (campaign_id, name, type text/number/money/date/choice/multi/person, settings jsonb with options / currencies / unit, position) and `task_field_values` (task_id, field_id, campaign_id copied by trigger, value jsonb), one row per task and field. Only main tasks have values. A field's type can't change; deleting a field deletes its values. Same permission rules as tasks. Choice and multi fields can colour their options (`settings.colors` = {option: colour}, Asana's colour names, `CHOICE_COLORS`; tokens `--choice-<name>-bg/-fg`; shown as `.choice-pill`, picked per option in the Fields dialog; the import keeps Asana's colours). Code: `js/fields.js` (types, value shapes, the ready-made sets Invoices / Requests / Bug tracker / Estimate taken from DSD's real Asana fields, inputs and formatting) and `js/fields-dialog.js` (the project's Fields dialog). In the List, number and money fields have a Total row per section and one for all sections (`refreshTotals` in `js/pages/campaign.js`; money summed per currency, never converted; counts the tasks shown). Shown in the task panel and as List columns, which editors fill in place (`saveListField` in `js/pages/campaign.js`; live redraws wait while a cell is being edited).
- **Sections (must-have 4, `14_sections.sql`):** `sections` (campaign_id, name, position) and `tasks.section_id` (null = "No section", shown first). Only main tasks have a section; the database clears it on subtasks and refuses a section from another project. Deleting a section keeps its tasks (set to null). Same permission rules as the project's tasks. Managed in the List and Board views (drag tasks between sections); projects have four views: List (no Status column, only the done tick: status lives in Kanban and the task panel; an All / Incomplete / Completed tasks filter, List only, kept in localStorage `list-done-filter`; the default the first time; after that a project opens in the view the person last picked, kept in localStorage `project-view`), Kanban (status columns), Board (section columns, cards show their status) and Calendar (month grid, Monday first, main tasks on their due date only; drag to another day changes `due_date`, + on a day adds a task due then; undated tasks are only counted; on phones it lists only days with tasks). In the List, sections open and close (▾ by the name, Collapse all / Expand all; closed ones kept per project in localStorage `closed-sections`, 'none' = No section; all open while searching or filtering). Board and List always offer + Add section. In List, Kanban and Calendar a section filter appears once sections exist, and new tasks go into the filtered section. A global `[hidden] { display: none !important; }` rule makes the hidden attribute always win.
- **Personal to-dos (`20_personal_todos.sql`, box in `js/pages/my-tasks.js`):** each admin/member has one project with `campaigns.personal_of` = their id (private, name "My to-dos"), made on first visit by `my_todos()`. Only that person can see it, Admins included (`person_can_see_campaign`, the campaigns policies and `personCanSee` all check `personal_of` first). It can't be shared, templated, reassigned or deleted by an Admin. Its budget is `internal` (`22_todos_are_internal.sql`), so hours on to-dos are internal time, never Education or Planning Center. Its tasks and subtasks are always assigned to its person (trigger `assign_personal_todos`, `21_todos_assigned_to_owner.sql`), so they also show in My tasks; the assignee pickers only offer that person. It shows as the My to-dos box at the top of My tasks (quick add and tick; clicking opens the task panel). There is no project page for it: `#/todos` redirects to My tasks and `renderCampaign` sends a personal project there too (Carlota: to-dos and My tasks only need a list); My tasks' "From projects" list leaves to-dos out. My tasks' header is one line like a project's (`.mytasks-head`: title, overdue / today / this week counts, Show completed, and this week's hours as a `.week-pill` linking to My time); the to-do add box sits on the My to-dos title line, and each task row is one line, with the project and its department side by side (hover for the full text). My tasks stays the landing page and where the logo goes (`homePath()`; directors land on Dashboards). Left out of the Projects list and Dashboards; keep it out of any new list of projects.
- **Private projects (must-have 7, `13_private_projects.sql`):** `campaigns.private` plus `campaign_access` rows (one person or one department each). Seen by those, the owner, the creator and every Admin; enforced in the database for projects, tasks, comments, files and notifications (`person_can_see_campaign` in SQL, `personCanSee` in `js/access.js`; keep them in step). Time entries stay readable so budget totals are right; the project's name is hidden ("Private project"). Assignees must be able to see the project.
- **Search (`js/search.js`, page `js/pages/search.js`, `#/search?q=`):** a box in the top bar (an icon on phones; press / to focus) for admins and members, with a suggestion list of matching people, projects and tasks while typing; picking a person opens `#/search?person=<id>`, their assigned tasks across visible, non-archived projects (`tasksAssignedTo()`) (`js/search-suggest.js`, `suggest()` in `js/search.js`). Each word typed is matched on its own, in any order (`searchWords()`; one `ilike` "contains" filter per word, all required, within one column; `hasAllWords()` does the same for lists already loaded, like a project's Find a task box). Queries run on project names and descriptions, section names, task titles and descriptions, and comment bodies, up to 30 of each; the database's permission rules (RLS) decide what comes back, so private projects stay hidden. No SQL needed. If it gets slow with many projects, add `pg_trgm` indexes.
- **On screen they're "projects"** (since 16 Nov 2026), but the code, database tables, columns and page addresses (`#/campaigns`) still say "campaign". Keep both as they are: only words people read say "project".
- **Archiving (must-have 3, `12_archive.sql`):** `campaigns.archived_at` / `archived_by`. Archived projects only show in the Archived tab, leave My tasks and the time pickers, still count in Dashboards, and the database refuses new time on them.
- **Departments (must-have 1, `11_departments.sql`):** business units are Education, DSD Center and Corporate; each department (Marketing, Education, Planning Center, Delight, Corporate, plus any the admin adds) belongs to one. Every person and campaign has a `department_id`; a campaign's `for_department_id` says who the work is for (own department by default). Marketing campaigns can be for any department; empty `for_department_id` = both Education and Planning Center, split by `team_settings.shared_split_education`. Marketing work for Delight counts against the Planning Center budget; for any other department, against neither budget (`budget = 'other'`) but still counts as campaign work in Marketing's capacity. Procurement is part of Corporate, not a separate department. There is no "Shared" label any more.
- The old `business_unit` columns on `campaigns` and `time_entries` are now `budget` (education / planning_center / shared / internal / other), set by the database, never typed. `other` = not one of Marketing's budgets. `internal` = internal time (no project, or someone's to-dos); reports label it **Corporate (internal)** (Carlota, 24 Nov), but it is still not a budget with hours of its own. Capacity, budgets, Team time, Dashboards and the Friday timesheet reminder are Marketing-only until must-have 11 (hours for every team). Helpers live in `js/departments.js`.
- Campaign time must always be on a task (constraint `campaign_time_needs_task`); only Internal time has no task. The project page's ▶ Start timer (time on the project as a whole, asked for by Marketing) logs on a main task titled "General work", created in In progress the first time (`startProjectTimer` in `js/pages/campaign.js`).
- **Asana import** (must-have 8): Carlota lists the projects to move. `tools/asana_fetch.py PROJECT_GID FOLDER` saves a whole project from Asana's API (token in `~/.asana_token`, Carlota's, never printed; delete it in Asana after go-live), and `tools/asana_import.py FOLDER --dept KEY [--for KEY|both] --out FILE.sql` turns it into import SQL, split into parts of about 300 KB for the Supabase editor (run in order). Import files live outside the repo (scratchpad), never in `supabase/migrations/`. Moves everything in each project, open and done, whatever its age (Carlota, 25 Nov), with subtasks, sections, custom fields, privacy and members; comments come as text ("From Asana · name · date", authored by the matching Atlas person, else Carlota, with the original date); files as links to Asana. Import files run inside `begin; set local atlas.importing = 'on'; … commit;` so `notify()` sends nothing (`25_asana_import_support.sql`). IDs are uuid5 of the Asana gid, so re-running doesn't duplicate. A subtask that Asana also lists as a row in the project is imported once, as a subtask (Carlota, 25 Nov); its field values go into its description. `campaigns.asana_url` / `tasks.asana_url` show as "Open in Asana". Delight's client coaching projects and history stay in Asana (free plan).
- **Task panel** (`js/pages/task-panel.js`), Asana-style (Carlota, 25 Nov): ✓ Mark complete button at the top left of the header (toggles status done/todo), title, then `.prop-row` label/value rows (Assignee, Due date, Project (square, name, then its section as a quiet dropdown, like Asana) , Status, Role in templates, then the project's custom fields), Description, Time, Subtasks, Files, Comments.
- **Forms (must-have 9, `26_forms.sql`, `js/forms.js`, `js/forms-dialog.js`, `js/pages/forms.js`):** a form belongs to a project (`forms`: name, intro, title_label, section_id, assignee_id, requestor_field_id, questions jsonb, active). Editors manage them with the project's **Forms** button; everyone signed in (directors too) sees them in **Forms** (`#/forms`, `#/forms/<id>`) through `list_forms()` / `get_form()` and sends them with `submit_form()` (security definer, so private projects work without giving access). The first question is the task title; each other question has a type (`QUESTION_TYPES`: text, choice, multi, date, number, file; `27_form_question_types.sql`; file answers are uploaded by the browser after `submit_form` returns the task id, allowed for the sender for 30 minutes by `form_files_allowed()` in `28_form_file_questions.sql`) with its own `options` when it goes to the description, and goes to a project field of a matching kind (`FIELDS_FOR_TYPE`), the due date (dates) or the description ("Label:\nanswer"); the description ends "Sent by … through the form … on …". Rules (must-have 10) will build on forms.
- **Rules (must-have 10, `29_rules.sql`, `js/rules.js`, `js/rules-dialog.js`):** per project (`rules`: name, active, trigger, conditions, actions jsonb; shapes in the migration's header). The project's **Rules** button lists them in words (`describeRule`) and edits them. The database runs them: triggers on tasks (added, section, status done, assignee, due date) and task_field_values call `run_rules()` (security definer), which checks conditions and calls `rule_action()` per action (assign, section, field, due in N days, status, comment, subtasks, week_section "Week of D Mon YYYY" made if missing, copy into another project with `tasks.copied_from`). Rules don't cascade (`atlas.running_rules`), imports skip them (`atlas.importing`), and `submit_form` runs them once its answers are saved (`atlas.no_rules`, `tasks.form_id`). Built in: subtasks take and follow their main task's assignee (`assign_subtask_from_parent`, `subtasks_follow_parent`).
- **Favourite projects (`30_favourite_projects.sql`, `js/favourites.js`):** `project_favourites` (person_id, campaign_id), each person's own (RLS). Loaded at sign-in into `state.favourites`; a ☆/★ `starButton()` before the name on the Projects page and in the project header (not templates or personal to-dos); favourites sort first on the Projects page; a ★ `.fav-menu` in the top bar (admins and members) lists them. Portfolios work the same (`33_favourite_portfolios.sql`, `portfolio_favourites`, `state.favouritePortfolios`, `starButton(id, name, 'portfolio')`), first on the Portfolios page and in their own group in the ★ menu.
- **Portfolios (`31_portfolios.sql`, `js/portfolios.js`, `js/pages/portfolios.js`, `#/portfolios`, `#/portfolios/<id>`):** like Asana's (Carlota, 26 Nov). `portfolios` (name, description, owner, private, asana_url), `portfolio_members` (who sees a private one), `portfolio_items` (a project or a child portfolio per row, position), `portfolio_fields` + `portfolio_field_values` (the portfolio's own columns, per item; same types as project fields, edited with the shared Fields dialog through the `PORTFOLIO_FIELDS` store). Seen by everyone unless private (`can_see_portfolio`); changed by admins/members, or for private ones by owner, members and Admins (`can_edit_portfolio`). Rows show status, owner, dates, tasks done, hours, then the columns, filled in place. A project's ⋯ menu has Add to portfolio…. In the menu for everyone (directors read-only).
- **Dashboards are for Admins and directors only** (`LEADS` in `js/app.js`, Carlota, 26 Nov): team members don't see the menu item and can't open `#/dashboards`.
- **Duplicate task** (task panel, main tasks only): copies the task with its subtasks, description, section, assignee, role and field values as To do, right after the original; a new due date shifts subtask dates. Comments, files and time aren't copied. Used for the Newsletter editions and Masters onboardings (Asana task templates).
- Capacity rules exist twice and must be kept in step: `js/capacity.js` (`availability`, `monthBudget`, `capacityPeople`) and the SQL functions `person_working_hours` / `unit_month_budget` (both count active Marketing people who count in capacity).
- When embedding a subtask's parent task in a Supabase request, name it by column (`parent:parent_id(...)`), not by constraint name.

## Design system

The tool's look is defined once, adapted from the BM design system (the BM skill itself needs React + Tailwind, which this tool doesn't use). The live reference is **Design system** in the menu under your photo (Admin only; `#/design-system`, `js/pages/design-system.js`).

- **Tokens only.** Colours, fonts, radius and shadows are CSS custom properties at the top of `css/styles.css`, with a dark-mode block. Never hard-code a colour in a page or component; add a token (with its dark value) if one is missing.
- **Fonts:** Inter for headings (`--font-display`), DM Sans for everything else (`--font`), loaded in `index.html`.
- **Accent:** `--accent` (`#0e7490` light / `#22d3ee` dark) for buttons and links, because BM's `#0891b2` is under 4.5:1 for text. `--accent-bright` (BM cyan) is only for focus rings, selected states and meters.
- **Reuse the existing building blocks** (`.btn` variants, `.field`, `.table`, `.card`, `.tag`, `.status`, `.status-chip`, `.view-switch`, `.empty-state`, `formDialog` / `confirmDialog` / `toast` in `js/ui.js`) rather than creating new ones. A new block gets added to the Design system page too.
- **Chart colours** (`--series-*`, `--status-*`) were validated for colour blindness with the dataviz palette script; re-run it before changing them.
- Colour never carries meaning alone: pair it with a word or icon.
